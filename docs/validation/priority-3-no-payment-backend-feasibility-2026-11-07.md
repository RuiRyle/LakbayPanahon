# Priority 3 — backend hosting without payment information

7 November 2026. **Research and planning only. Stage 1 billing activation is ON HOLD. The accepted Stage 0 candidate is unchanged. Priority 4 is excluded.

## Finding and recommendation

Legitimate free compute options exist without a payment instrument. That does **not** yet establish a reliable, fully compatible 30-student assessment service. No provider was tested with this backend, and no account-specific signup/anti-abuse checks were performed.

**Recommended engineering path: investigate a separate local Netlify Node-functions adapter first**, subject to confirming current no-card onboarding before any later account creation. It has a closer runtime fit than Workers and a hard free-usage limit. Do not deploy it or replace the accepted candidate now. **Cloudflare Workers has the clearest current explicit no-card statement**, but requires a more substantial compatibility investigation. Render is suitable for a disposable compatibility experiment, not the recommended classroom host. No researched option currently passes all existing release gates.

The safest action available today is to keep testing locally while retaining existing production records and the accepted candidate. This is not a claim that the legacy production reward mechanism is secured merely because deployment is deferred.

## Initial 30-student usage estimates

Use the prior 20-school-day workload: 20 new mission quizzes, five retries, four chapter challenges, ten dailies and twenty restores per student. Including transport headroom this is about **12,780 backend calls/month**, or 639/day averaged across school days. Thirty simultaneous saves is a separate burst requirement; a daily request quota is not evidence that a burst is supported.

For Netlify, use its current credit accounting, not obsolete 125K-invocation/300-build-minute limits. Four production publications cost 60 credits. At 12,780 calls, assumed 0.5–2 seconds and **1–2 GB** allocated memory, compute uses about 18–142 credits. Add approximately 2.6 request credits and 20 credits for a hypothetical 1 GB of responses: **roughly 100–225 of 300 credits/month**. This is a conditional arithmetic example, not a benchmark. Eight publications instead add 60 credits, nearly consuming the high-end allowance. Cold starts, OPTIONS, retries, other projects and larger responses can exhaust it. Keep website/media on Firebase Hosting. [Current metering](https://docs.netlify.com/manage/accounts-and-billing/billing/billing-for-credit-based-plans/how-credits-work/).

Netlify memory/CPU choices differ from the accepted Cloud Run configuration; its documented memory range starts at 1024 MB. Do not assume Cloud Run max-two/concurrency-eight or 256 MiB settings transfer unchanged. [Function resources](https://docs.netlify.com/build/functions/configuration/).

For Workers, estimated request volume is far below 100K/day, but **10 ms CPU per call** is the important unknown for cryptographic verification, catalog handling, grading and serialization. Waiting for Firestore is not equivalent to CPU time. Emulator wall-clock latency cannot establish this limit. For Render, single-instance 0.1 CPU plus wakeup delay is the concern, not monthly hours alone. No production latency or availability promise is justified for any option.

## Firebase still constrains a completely free system

- **Firestore Spark:** 50K reads/day, 20K writes/day, 1 GiB stored and 10 GiB/month outbound are shared with the existing app. The conservative earlier model is **54K assessment reads and 1,650 writes per school day**. That is already 4K reads above the daily allowance before lessons/teachers. The model is not measured post-Option-A billing, so it establishes a feasibility concern, not inevitable failure. Meter actual returned documents, queries/retries/index costs and shared UI traffic before a free pilot. Admin credentials do not bypass quotas. [Firestore limits](https://firebase.google.com/docs/firestore/quotas).
- A proposed planning target could reserve at least 15K daily reads for existing app activity and keep assessments below 35K. This is **not implemented and not a proven sufficient reserve**. Any catalog/history caching or query reduction must preserve fresh digest/prerequisite/status/reward verification. Do not silently reduce features or skip checks to fit a quota.
- **Auth/App Check:** existing Firebase users can remain. Firebase supports Admin servers outside Google and App Check verification on custom backends. The existing App Check key mismatch still needs its separately approved repair and real attestation; moving servers does not fix it. Keep the frontend on its existing registered Firebase origins. A backend's hostname is not itself a new browser attestation origin. [Admin setup](https://firebase.google.com/docs/admin/setup), [custom-backend App Check](https://firebase.google.com/docs/app-check/custom-resource-backend).
- **Attestation quota:** about 1,200–2,400 checks/month is plausible for this class, but the free 10K allowance is organizational. With no billing, excess can reject requests with 429 until reset; tokens are not purchased once per quiz answer. Do not disable enforcement as a workaround. [Provider billing/quota](https://docs.cloud.google.com/recaptcha/docs/billing-information).
- **Website/media/storage:** retain Firebase Hosting, Auth, catalog and saved records. Hosting limits and any existing AI/TTS/provider charges remain independent. A free backend does not certify the entire application is free. Current Cloud Storage for Firebase requirements and prior managed backup/export requirements cannot be bypassed by changing compute host. [Hosting](https://firebase.google.com/docs/hosting/usage-quotas-pricing), [Storage](https://firebase.google.com/docs/storage/faqs-storage-changes-announced-sept-2024).
- **Recovery:** managed Firestore export/import requires billing. A no-billing route needs a separately reviewed equivalent recovery arrangement, potentially an authorized bounded Admin read/export to encrypted owner-held storage plus an isolated restore test. That would consume quota, process learner data and need approval; it is not done here. Configuration hashes and public catalog snapshots are not learner backups. [Managed export requirement](https://firebase.google.com/docs/firestore/manage-data/export-import).

When a free provider or Firebase quota is exhausted, fail closed and pause saving. A transaction must either commit atomically or not pay. A lost acknowledgement must be recovered from its private receipt using the same ID once reads are available. Uncommitted attempts can expire during an outage; explain restart requirements while retaining earned progress. **All-endpoint throttling is still absent**; a hard free quota prevents some charges by turning abuse into an availability outage instead.

## Required architectural changes and risks

1. **Reuse one trusted service.** Keep the accepted issuance/grading/adaptive/prerequisite/reward core, same canonical IDs and existing Firestore database. Do not migrate balances or introduce a second reward authority. Reuse the existing SDK transaction adapter on a compatible Node host; a Workers REST adapter needs a separately approved parity/retry/atomicity design.
2. **Adapt transport only where possible.** Bridge the four `onCall` wrappers to the host's HTTP interface, preserving callable envelopes, CORS, headers, invalid-token rejection, Auth revocation, active-user authorization and App Check. Never accept a client UID or decoded-but-unverified token as identity. Demonstrate the adapter rather than exposing raw handlers. Frontend callable URL routing and a narrow CSP origin would need changes; the visible interface/content need not change. No migration is required merely to change endpoint URLs.
3. **Replace managed ADC delivery safely.** The gcloud runtime/build-account bindings do not apply on external hosts. Design least-privilege workload federation if actually supported at runtime; otherwise a narrowly scoped service-account key would need explicit approval, host secret storage, rotation and incident handling. Never ship keys in browser bundles/repositories or use the default privileged account. External Admin authority still bypasses Firestore client rules and needs all existing server checks. No key has been exported.
4. **Keep the database boundary protected.** A later rollout still requires restrictive canonical/private-record rules, retiring alternate raw reward endpoints, a disabled protocol and a reviewed cutover/rollback. External compute does not secure currently permissive rules automatically. Use the same deny-only rollback principle, not an insecure old frontend.
5. **Review student-data handling.** Even without copying the database, an external host processes identifiers/answers and holds privileged credentials. Approve the provider/access/logging/retention arrangement and avoid logging tokens or answers. Provider secret stores and limits do not make public repositories safe for credentials.

These are a new deployment/transport/identity design, **not** a configuration-only extension of accepted Stage 0. Serverless cold starts, Firestore regional round trips, provider suspension, expired attempts, package limits, account restrictions and private-receipt recovery all require fresh proof. No runtime/dependency/assessment change is implemented by this report.
